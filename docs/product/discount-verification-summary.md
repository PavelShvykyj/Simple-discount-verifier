# Описание текущего проекта

## 1. Саммери текущего процесса

### 1.1. Общая идея приложения

Мы строим веб-сервис для ресторанного бизнеса, который помогает подтвердить право клиента на получение скидки через номер телефона и одноразовый штрихкод.

Администратор заранее создаёт анкету клиента и указывает номер телефона. При получении скидки клиент самостоятельно вводит свой номер телефона в публичном веб-приложении. Система ищет сохранённую анкету по этому номеру. Если анкета существует, система отправляет SMS-код на этот номер. После успешного подтверждения SMS создаётся короткоживущий одноразовый штрихкод, связанный с этим же телефоном.

Сервис не рассчитывает размер скидки сам.
Размер скидки рассчитывается основным ресторанным бизнес-приложением на основании существующей дисконтной карты.

Наш веб-сервис отвечает за:

- хранение анкет клиентов, которым разрешена скидка;
- подтверждение клиентом контроля номера телефона через SMS;
- выдачу короткоживущего одноразового кода;
- отображение этого кода как штрихкода;
- проверку кода по запросу основного бизнес-приложения;
- возврат номера телефона / lookup key для поиска дисконтной карты;
- защиту от повторного использования кода;
- логирование всей цепочки.

## 2. Участники процесса

| Участник | Функция |
| --- | --- |
| Администратор заведения | Один раз создаёт анкету клиента, когда принято решение, что клиент имеет право на скидку |
| Клиент | В момент получения скидки вводит телефон, подтверждает его через SMS и показывает штрихкод |
| Основное ресторанное бизнес-приложение | Сканирует штрихкод, отличает веб-код от обычной дисконтной карты, проверяет код через API и рассчитывает скидку |
| Веб-сервис скидок | Хранит анкеты, отправляет SMS, создаёт и проверяет одноразовые коды |

## 3. Процесс A — создание анкеты

Анкета создаётся заранее и является отдельным процессом от получения скидки.

Бизнес-смысл анкеты:

Клиент был заранее признан имеющим право на скидку.

Процесс:

1. Администратор открывает административную часть веб-приложения.
2. Администратор заполняет анкету клиента.
3. Администратор вводит номер телефона клиента.
4. Анкета сохраняется.
5. Клиент считается имеющим право на скидку.

На старте реализации:

- SMS-подтверждение телефона при создании анкеты не делаем;
- телефон вводится администратором вручную;
- возможная ошибка ввода телефона принимается как ограничение первой версии.

Фаза 2:

- добавить SMS-подтверждение телефона при создании анкеты;
- это будет защита от ошибки ввода номера администратором.

## 4. Процесс B — получение скидки

Этот процесс происходит уже в момент расчёта клиента.

Процесс:

1. Клиент открывает публичную страницу веб-приложения.
2. Клиент самостоятельно вводит свой номер телефона.
3. Система создаёт `correlationId` для этой попытки и возвращает его на фронт
   уже в ответе первого запроса, если это технически возможно, независимо от
   бизнес-результата запроса.
4. Фронт сохраняет `correlationId` и по специальной кнопке может сформировать
   QR для администратора. Это позволяет передать админу ситуацию даже если
   проблема возникла до формирования штрихкода.
5. Система проверяет, существует ли анкета с таким номером.
6. Если анкета не найдена — скидочный процесс не продолжается.
7. Если анкета найдена — система отправляет SMS-код на этот же номер.
8. Клиент вводит SMS-код.
9. Если SMS-код неверный — скидочный процесс не продолжается.
10. Если SMS-код верный — система генерирует случайный одноразовый код, связанный с подтверждённым телефоном.
11. Код отображается клиенту как штрихкод.
12. Клиент показывает штрихкод кассиру / оператору.
13. Основное ресторанное приложение сканирует штрихкод.
14. Основное приложение определяет тип штрихкода:
    - обычная дисконтная карта EAN13;
    - веб-код приложения в формате Code 128 с префиксом.
15. Если это обычная дисконтная карта — используется старый стандартный процесс.
16. Если это веб-код — основное приложение вызывает API веб-сервиса.
17. Веб-сервис проверяет код.
18. Если код валиден и не истёк — веб-сервис возвращает номер телефона / lookup key.
19. Веб-сервис сразу очищает или инвалидирует одноразовый код.
20. Основное приложение ищет дисконтную карту / анкету по номеру телефона.
21. Если карта найдена — основное приложение рассчитывает и применяет скидку.
22. Если карта / анкета не найдена в основной системе, основное приложение может
    по запросу получить данные сохранённой анкеты из веб-сервиса по этому
    телефону.
23. После получения анкеты основное приложение создаёт или дополняет локальную
    запись по своим правилам и остаётся ответственным за поиск карты и расчёт
    скидки.

## 5. Ключевые бизнес-правила

### Анкета

- Анкета создаётся один раз, заранее.
- Анкета означает, что клиент имеет право на скидку.
- Анкета либо сохранена, либо её нет.
- Один номер телефона соответствует одному человеку и одной анкете.
- Номер телефона является отдельным системным полем анкеты и используется для
  уникальности, SMS-проверки и связи с дисконтной картой.
- Текущий состав анкеты: ФИО, день рождения, любимое блюдо.
- Пункты анкеты хранятся и передаются как список `code`, `name`, `value`.
- Тип значения пункта анкеты не хранится и не передаётся в API веб-сервиса.
- Версии анкеты не используются.
- Сложные статусы анкеты не нужны.
- Статус Draft не нужен.
- Статусы синхронизации анкеты не нужны.
- Веб-сервис является источником новых анкет.

### Телефон

- Номер телефона является основным идентификатором клиента для связи с дисконтной картой.
- На старте телефон в анкете не подтверждается через SMS.
- В момент получения скидки клиент обязан подтвердить контроль номера телефона через SMS.
- SMS-проверка в момент получения скидки доказывает, что скидку получает человек, контролирующий нужный телефонный номер.

### Разовый штрихкод

- Разовый код создаётся только после успешного SMS-подтверждения телефона.
- Код случайно генерируется.
- Код отображается как штрихкод.
- Код должен быть короткоживущим.
- Рекомендуемое время жизни: 3 минуты, конфигурируемо.
- Код используется один раз.
- Если клиент запрашивает новый код при наличии активного кода, веб-сервис пересоздаёт код и перезаписывает активную запись в таблице.
- Временное состояние получения скидки хранится как одна текущая runtime-запись
  на телефон; новый запрос для того же телефона перезаписывает предыдущий SMS
  challenge и предыдущий barcode.
- После успешной проверки основным приложением код очищается / инвалидируется.
- Код не должен использоваться повторно.
- Код нужен не для расчёта скидки, а для подтверждения, что скидку получает именно клиент, подтвердивший телефон.

TTL — это Time To Live, то есть время жизни временного объекта. В нашем случае это срок, в течение которого одноразовый штрихкод считается действительным.

### Штрихкод

- Обычные дисконтные карты остаются в формате EAN13.
- Веб-код отображается в формате Code 128.
- Веб-код не содержит префикс: POS отличает его по длине.
- Маршрутизация POS по длине: EAN13 - 13 символов, обычная карта - 18
  символов, web-code приложения - 20 символов.
- Веб-код содержит полный 10-символьный технический ключ телефона и полный
  10-символьный `correlationId` в формате
  `<phoneRuntimeKey10><correlationId10>`, чтобы POS мог быстро проверить код, а
  поддержка могла быстро найти всю цепочку событий по barcode на месте.
- Для админского сценария просмотра информации по попытке получения скидки
  подтверждён QR-код. Основной QR формируется фронтом по `correlationId`,
  полученному после первого публичного запроса, и может быть показан даже до
  генерации штрихкода. QR не является ссылкой на админскую страницу: он
  содержит нейтральный текстовый payload
  `SDV-SUPPORT:v1:<correlationId10>`. Админское приложение само разбирает этот
  payload и отправляет авторизованный запрос inspect. Если штрихкод уже
  сформирован, админский интерфейс также может найти ту же цепочку по
  `correlationId`, извлечённому из последних 10 символов barcode. Ручной "код
  поддержки" в текущий scope не входит.
- EAN13 — числовой штрихкод из 13 цифр, часто используемый для товаров и карт.
- Code 128 — формат штрихкода, который может кодировать буквы, цифры и специальные символы.
- Для генерации и проверки совместимости Code 128 используется `@bwip-js/browser`.

Нужно проверить:

- поддерживают ли сканеры Code 128;
- корректно ли основное приложение получает строку от сканера;
- можно ли надёжно отрисовать Code 128 в веб-приложении.
- может ли администратор на странице `scanner-survey` камерой мобильного
  браузера прочитать QR-код / тестовый код, отображённый в другом инстансе
  приложения. Для Angular-реализации проверки чтения использовать
  `@zxing-js/ngx-scanner`, так как пакет `@zxing/browser` рекомендует его для
  Angular-приложений.

### Основное бизнес-приложение

- Основное приложение не предоставляет публичный API.
- Оно может быть REST-клиентом.
- Поэтому основное приложение при сканировании веб-кода обращается к API веб-сервиса.
- Анкеты не синхронизируются в основное приложение заранее.
- Если веб-код валиден, но основное приложение не нашло локальную дисконтную
  карту / анкету по возвращённому телефону, оно может отдельным запросом
  получить данные анкеты из веб-сервиса по этому телефону.
- API для основного POS/ресторанного приложения является server-to-server
  интеграцией и использует HMAC-проверку внутри Azure Function.
- POS-запросы передают заголовки `x-client-id`, `x-timestamp` и `x-signature`.
- Начальный client id: `main-pos-system`.
- В этой фазе replay-защита опирается на проверку свежести `x-timestamp`.
- В будущей фазе добавим `nonce`, таблицу использованных nonce и
  периодическую очистку этой таблицы.
- POS-запрос проверки barcode передаёт обязательный `scanId` — уникальный
  идентификатор операции сканирования / продажи на стороне POS.
- Если POS повторяет тот же запрос проверки после timeout или сетевого сбоя, он
  обязан передать тот же `scanId`; backend вернёт повторный успешный результат
  для уже использованного barcode, если `scanId` совпадает.
- Если barcode уже использован другим `scanId`, backend возвращает отказ
  `already_used`.
- Скидка рассчитывается только основным ресторанным приложением.
- Веб-сервис не рассчитывает размер скидки.
- Веб-сервис возвращает телефон как lookup key для поиска дисконтной карты.
- Сопоставление происходит по номеру телефона.

### Защита от мошенничества

Главный риск — злоупотребления со стороны персонала заведения.

Поэтому:

- код живёт максимально коротко;
- код одноразовый;
- код очищается после успешной проверки;
- код нельзя использовать повторно;
- код связан с подтверждённым телефоном;
- веб-код отличается от обычной дисконтной карты;
- вся цепочка должна логироваться.
- Администратор может просмотреть служебную информацию по конкретной попытке
  получения скидки через `correlationId`: текущий статус процесса, анкету при
  наличии, audit-события, данные barcode при наличии, `ConsumedByScanId` и
  разобранный контекст `scanId`, если формат `scanId` известен.
- Административное принудительное разрешение barcode не входит в текущий scope;
  это оставлено как возможная будущая функция.

### Логирование

С момента первого запроса на получение скидки должна быть прослеживаемая
цепочка событий.

Correlation ID — это общий идентификатор цепочки операций. Он позволяет связать
между собой события одного процесса: старт попытки, поиск анкеты, отправку SMS,
проверку SMS, генерацию штрихкода, сканирование и проверку кода.

Номер телефона лучше не использовать как сам correlationId.

Лучше хранить:

- correlationId — случайный идентификатор процесса;
- phoneHash — хеш номера телефона для поиска в логах без хранения номера в открытом виде.

Для поддержки на месте `correlationId` возвращается фронту уже после первого
публичного запроса. По специальной кнопке фронт формирует QR на основе
`correlationId` для передачи администратору. QR содержит текстовый payload
`SDV-SUPPORT:v1:<correlationId10>`, а не ссылку, чтобы клиент при случайном
сканировании не уходил в служебную авторизацию и не терял состояние публичного
процесса. Когда web-barcode уже создан, `correlationId` также входит в значение
barcode, чтобы по сообщённому barcode можно было открыть ту же цепочку
audit-событий.

Trade-off по длине barcode:

- На scanner-survey хуже читался длинный 28-символьный Code 128, поэтому
  целевой web-code ограничен 20 символами.
- Дополнительная таблица barcode-index позволила бы сделать visible code еще
  короче, но добавила бы запись в две таблицы, eventual consistency и отдельную
  очистку.
- Выбранный формат 10+10 сохраняет один point read в `DiscountRuntime` без
  дополнительной таблицы.
- При 10 base32 символах пространство значений равно `32^10`. Для 10 000
  активных/неочищенных runtime rows вероятность хотя бы одной коллизии
  phone-key порядка `0.0000044%`.
- При 2000 попыток в день и 30 днях истории это около 60 000 `correlationId`;
  вероятность хотя бы одной коллизии в таком горизонте порядка `0.00016%`.
