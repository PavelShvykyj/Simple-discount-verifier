# POS-процесс получения скидки через веб-штрихкод

Дата фиксации контекста: 2026-07-07.

Этот документ фиксирует текущий контекст обсуждения POS-части проекта. Он
описывает бизнес-порядок действий ресторанного приложения, реализованного на
1С 8.3.9 в клиент-серверной архитектуре, толстый клиент, обычные формы.

## Граница ответственности POS

POS не подтверждает телефон клиента и не выпускает веб-штрихкод. Эти действия
выполняет веб-сервис скидок.

POS отвечает за то, чтобы после сканирования веб-штрихкода превратить его в
обычный для ресторанного приложения сценарий: найти или создать локальную
дисконтную карту / клиента и рассчитать скидку своими существующими правилами.

Главная бизнес-идея:

```text
веб-штрихкод -> подтвержденный телефон -> локальная карта/анкета -> стандартный расчет скидки POS
```

## Точка входа в 1С

Точкой входа считается клиентская форма обработки, подключенная к процессу
сканирования штрихкода.

Условная логика входа:

```bsl
Если ЭтоВебШтрихкод(СчитанныйШтрихкод) Тогда
    ВызовПроцедурыМодуля();
КонецЕсли;
```

Если считанный штрихкод не является веб-штрихкодом нашего сервиса, POS должен
продолжать существующий стандартный сценарий обработки обычной дисконтной
карты.

## Связи справочников

Центральная сущность POS-процесса - `Справочник.ДисконтныеКарты`.
Именно ссылку на дисконтную карту должен вернуть проектируемый модуль при
успешной обработке веб-штрихкода.

`Справочник.ДисконтныеКарты` подчинен `Справочник.Контрагенты`. При создании
нового контрагента для клиента из веб-сценария POS использует ФИО, полученное
из анкеты веб-сервиса.

`Справочник.ДисконтныеКарты` содержит ссылку на `Справочник.Скидки`.
`Справочник.Скидки` описывает правило расчета скидки, а POS применяет это
правило уже своим существующим механизмом пересчета заказа.

`Справочник.АнкетныеДанные` хранит значения анкеты как отдельные строки,
подчиненные конкретной дисконтной карте. Каждая строка содержит ссылку на
`ПланВидовХарактеристик.ПунктыАнкетПотребителей` и значение этого пункта.

`ПланВидовХарактеристик.ПунктыАнкетПотребителей` определяет состав полей
анкеты. Для поиска локальной дисконтной карты по телефону POS должен идти от
пункта анкеты с типом/назначением "телефон" и искать строку `АнкетныеДанные`
по точному совпадению значения телефона.

Пункт анкеты, который отвечает за телефон, ФИО, дату рождения и другие
согласованные поля, не нужно определять по строковому наименованию. Его можно
получать через `Константы.ЛойалКардНастройки`: значение константы указывает на
элемент `Справочник.ЛойалКардПараметры`, а в этом элементе есть реквизиты
`ПунктФИО`, `ПунктДатаРождения`, `ПунктТелефон`, `ПунктИД` и
`ПунктСерийНыйНомер`. Это настройки другой интеграции, но для нашего модуля их
допустимо использовать как источник соответствия между бизнес-полями и
`ПунктыАнкетПотребителей`.

После найденной строки `АнкетныеДанные` POS получает ее владельца. Владелец
этой строки и есть нужная `СправочникСсылка.ДисконтныеКарты`.

## Правила поиска и создания дисконтной карты

Поиск локального дисконта начинается не с реквизита `КодКарты`, а с анкетных
данных:

1. POS берет телефон, возвращенный веб-сервисом после успешной проверки
   веб-штрихкода.

2. POS нормализует телефон к виду "только цифры", без символа `+`.

3. POS получает пункт анкеты, который соответствует телефону, из
   `Константы.ЛойалКардНастройки.ПунктТелефон`.

4. POS ищет `АнкетныеДанные` по точному совпадению:
   - `ПунктАнкеты` - найденный пункт телефона;
   - `Значение` - телефон только цифрами.

5. Если строка `АнкетныеДанные` найдена, POS берет ее владельца как найденную
   дисконтную карту.

6. Если дисконтная карта найдена и не заблокирована, проектируемый модуль
   возвращает ее вызывающей форме.

Если локальная дисконтная карта еще не существует, POS создает ее по анкете,
полученной из веб-сервиса:

1. Создать или определить локального контрагента.

2. В качестве наименования контрагента использовать ФИО из анкеты веб-сервиса.

3. Создать `Справочник.ДисконтныеКарты` с владельцем-контрагентом.

4. В реквизитах `КодКарты` и `РучнойКод` записать телефон клиента в формате
   "только цифры", без символа `+`.

5. Заполнить остальные согласованные реквизиты дисконтной карты: правило
   скидки, вид карты, дату выдачи и другие значения по правилам POS.

6. Создать или обновить строки `АнкетныеДанные` для этой карты по пунктам
   анкеты. Соответствие бизнес-полей и пунктов анкеты берется из
   `Константы.ЛойалКардНастройки`, включая телефон и ФИО.

7. После создания карты вернуть ее как обычную локальную дисконтную карту.

## Результат основного модуля

Основная функция проектируемого модуля возвращает `Соответствие`:

- `Результативность` - булево.
- `Описание` - `"Ок"` при успешном выполнении; при ошибке сообщение для
  пользователя на украинском языке.
- `Данные` - `СправочникСсылка.ДисконтныеКарты`, найденная или созданная
  локальная дисконтная карта.

## Правила разработки модуля

При реализации POS-модуля нужно придерживаться практичного стиля 1С-кода:
минимум лишней обвязки, минимум повторных обращений к базе, максимум данных для
принятия решения получать одним осмысленным запросом.

### Не делать лишних проверок

Проверки должны защищать реальные границы процесса: пустой телефон,
неуспешный ответ веб-сервиса, отсутствие дисконтной карты, заблокированную
карту, невозможность создать локальные данные.

Не нужно дублировать одно и то же условие разными способами.

Плохо:

```bsl
Если ЗначениеЗаполнено(Телефон) Тогда
    Если Телефон <> "" Тогда
        Если СтрДлина(Телефон) > 0 Тогда
            // Работаем дальше
        КонецЕсли;
    КонецЕсли;
КонецЕсли;
```

Хорошо:

```bsl
Если Не ЗначениеЗаполнено(Телефон) Тогда
    Возврат Ошибка("Не вказано телефон клієнта");
КонецЕсли;
```

Плохо:

```bsl
ДисконтнаяКарта = НайтиДисконтПоТелефону(Телефон);

Если ТипЗнч(ДисконтнаяКарта) = Тип("СправочникСсылка.ДисконтныеКарты") Тогда
    Если ЗначениеЗаполнено(ДисконтнаяКарта) Тогда
        // Работаем дальше
    КонецЕсли;
КонецЕсли;
```

Хорошо:

```bsl
ДисконтнаяКарта = НайтиДисконтПоТелефону(Телефон);

Если Не ЗначениеЗаполнено(ДисконтнаяКарта) Тогда
    Возврат Ошибка("Дисконтну картку не знайдено");
КонецЕсли;
```

### Не создавать функции из одной строки

Функция должна иметь самостоятельный смысл: нормализовать телефон, выполнить
HTTP-запрос, разобрать ответ, сформировать результат, найти или создать
локальные данные.

Однострочные функции-обертки не добавляют ясности и только дробят код.

Плохо:

```bsl
Функция ПолучитьПунктТелефон()
    Возврат Константы.ЛойалКардНастройки.Получить().ПунктТелефон;
КонецФункции
```

Хорошо:

```bsl
НастройкиЛойалКард = Константы.ЛойалКардНастройки.Получить();
ПунктТелефон = НастройкиЛойалКард.ПунктТелефон;
```

Плохо:

```bsl
Функция ЭтоПустаяКарта(Карта)
    Возврат Не ЗначениеЗаполнено(Карта);
КонецФункции
```

Хорошо:

```bsl
Если Не ЗначениеЗаполнено(ДисконтнаяКарта) Тогда
    Возврат Ошибка("Дисконтну картку не знайдено");
КонецЕсли;
```

### Получать данные из базы преимущественно запросами

Если нужны данные из базы, приоритетно использовать `Запрос`, а не цепочки
обращений к объектам и ссылкам через точку.

Плохо:

```bsl
ДисконтнаяКарта = НайденныеАнкетныеДанные.Владелец;
ФИО = ДисконтнаяКарта.Владелец.Наименование;
Скидка = ДисконтнаяКарта.Скидка;
```

Хорошо:

```bsl
Запрос.Текст =
"ВЫБРАТЬ
|   АнкетныеДанные.Владелец КАК ДисконтнаяКарта,
|   АнкетныеДанные.Владелец.Владелец.Наименование КАК ФИО,
|   АнкетныеДанные.Владелец.Скидка КАК Скидка
|ИЗ
|   Справочник.АнкетныеДанные КАК АнкетныеДанные
|ГДЕ
|   АнкетныеДанные.ПунктАнкеты = &ПунктТелефон
|   И АнкетныеДанные.Значение = &Телефон";
```

Плохо:

```bsl
КартаОбъект = ДисконтнаяКарта.ПолучитьОбъект();

Если КартаОбъект.Заблокирована Тогда
    Возврат Ошибка("Дисконтну картку заблоковано");
КонецЕсли;
```

Хорошо:

```bsl
Запрос.Текст =
"ВЫБРАТЬ
|   ДисконтныеКарты.Ссылка КАК Ссылка,
|   ДисконтныеКарты.Заблокирована КАК Заблокирована
|ИЗ
|   Справочник.ДисконтныеКарты КАК ДисконтныеКарты
|ГДЕ
|   ДисконтныеКарты.Ссылка = &ДисконтнаяКарта";
```

### Предпочитать комплексный запрос нескольким простым

Если для решения нужны связанные данные, лучше получить их одним запросом:
дисконтную карту, владельца, признак блокировки, правило скидки и нужные
анкетные значения.

Плохо:

```bsl
ДанныеАнкеты = НайтиАнкетныеДанныеПоТелефону(Телефон);
ДисконтнаяКарта = ДанныеАнкеты.Владелец;
Контрагент = ДисконтнаяКарта.Владелец;
Скидка = ДисконтнаяКарта.Скидка;
```

Хорошо:

```bsl
Запрос.Текст =
"ВЫБРАТЬ
|   АнкетныеДанные.Владелец КАК ДисконтнаяКарта,
|   АнкетныеДанные.Владелец.Владелец КАК Контрагент,
|   АнкетныеДанные.Владелец.Скидка КАК Скидка,
|   АнкетныеДанные.Владелец.Заблокирована КАК Заблокирована
|ИЗ
|   Справочник.АнкетныеДанные КАК АнкетныеДанные
|ГДЕ
|   АнкетныеДанные.ПунктАнкеты = &ПунктТелефон
|   И АнкетныеДанные.Значение = &Телефон";
```

Плохо:

```bsl
ПунктТелефон = Настройки.ПунктТелефон;
ПунктФИО = Настройки.ПунктФИО;

ФИО = НайтиЗначениеАнкеты(ДисконтнаяКарта, ПунктФИО);
Телефон = НайтиЗначениеАнкеты(ДисконтнаяКарта, ПунктТелефон);
ДатаРождения = НайтиЗначениеАнкеты(
    ДисконтнаяКарта,
    Настройки.ПунктДатаРождения);
```

Хорошо:

```bsl
Запрос.Текст =
"ВЫБРАТЬ
|   АнкетныеДанные.ПунктАнкеты КАК ПунктАнкеты,
|   АнкетныеДанные.Значение КАК Значение
|ИЗ
|   Справочник.АнкетныеДанные КАК АнкетныеДанные
|ГДЕ
|   АнкетныеДанные.Владелец = &ДисконтнаяКарта
|   И АнкетныеДанные.ПунктАнкеты В (&ПунктыАнкеты)";
```

## Happy path

1. Кассир сканирует штрихкод в форме продажи или в форме обработки,
   связанной с продажей.

2. Клиентская форма получает строку сканера как считанный штрихкод.

3. POS определяет тип штрихкода.

4. Если это обычная дисконтная карта, POS идет по старому существующему
   процессу.

5. Если это веб-штрихкод нашего сервиса, POS не запускает сразу обычный поиск
   дисконтной карты по номеру карты.

6. Клиентская форма передает веб-штрихкод в серверную процедуру модуля
   обработки.

7. POS формирует идентификатор операции сканирования, связанный с текущей
   продажей / чеком / заказом.

8. POS проверяет веб-штрихкод через веб-сервис скидок.

9. Веб-сервис подтверждает, что штрихкод действительный, не истек и еще не
   использован.

10. Веб-сервис возвращает POS номер телефона как ключ поиска клиента.

11. POS нормализует телефон к виду "только цифры", без символа `+`.

12. POS ищет в своей базе дисконтную карту через `АнкетныеДанные`: по пункту
    анкеты "телефон" и точному совпадению значения телефона.

13. Если дисконтная карта найдена, POS использует ее как обычную карту клиента.

14. POS рассчитывает скидку своими существующими правилами.

15. POS применяет скидку к текущей продаже.

16. Кассир продолжает оформление продажи без отдельного нового бизнес-процесса.

17. Если локальная карта по телефону еще не найдена, POS получает из
   веб-сервиса сохраненную анкету клиента по этому телефону.

18. POS создает или дополняет локального контрагента по ФИО из анкеты.

19. POS создает локальную дисконтную карту: `КодКарты` и `РучнойКод`
   заполняются телефоном клиента в формате "только цифры".

20. POS заполняет анкетные данные созданной карты, включая телефон.

21. После создания или дополнения локальной записи POS повторяет стандартный
   внутренний сценарий: найти карту по телефону и применить скидку.

22. С этого момента продажа дальше живет как обычная продажа с обычной
   дисконтной картой.

23. POS сохраняет у себя связь текущей продажи с операцией сканирования,
   телефоном и найденной или созданной картой, если это нужно для последующего
   разбора ситуации.

24. Если POS повторяет проверку из-за таймаута или сетевого сбоя, он использует
   тот же идентификатор операции сканирования для той же продажи.

25. Если веб-сервис уже принял этот штрихкод для той же операции сканирования,
   POS получает повторный успешный результат и продолжает тот же сценарий.

26. После успешной проверки веб-штрихкод считается использованным.

27. Тот же веб-штрихкод не должен применяться в другой продаже.

28. Завершение продажи, отмена продажи или пересчет скидки дальше
   обрабатываются обычными правилами POS.

29. Использованный веб-штрихкод при отмене продажи не восстанавливается.

## Важные договоренности

- Для кассира веб-штрихкод должен выглядеть как короткое ответвление, которое
  приводит к обычному применению дисконтной карты.
- Расчет скидки остается полностью на стороне ресторанного приложения.
- Веб-сервис не передает размер скидки и не принимает решение о сумме скидки.
- POS не синхронизирует анкеты заранее.
- POS получает анкету из веб-сервиса только по необходимости: после успешной
  проверки веб-штрихкода, если локальная карта / клиент не найдены по телефону.
- Локальный поиск дисконта по телефону выполняется через `АнкетныеДанные`, а
  не напрямую через реквизиты дисконтной карты.
- При создании новой дисконтной карты телефон без `+`, только цифрами,
  записывается в `КодКарты` и `РучнойКод`.
- При создании контрагента используется ФИО из анкеты веб-сервиса.
- Для определения пунктов анкеты телефона, ФИО и других согласованных полей
  допустимо использовать `Константы.ЛойалКардНастройки` и связанный элемент
  `Справочник.ЛойалКардПараметры`.
- Повторная проверка после технического сбоя должна относиться к той же
  продаже, а не создавать новое использование штрихкода.
- Использованный веб-штрихкод одноразовый и не возвращается в активное
  состояние после отмены продажи.
