# Azure Table Storage Design

This document fixes the approved Azure Table Storage design for the MVP
discount verification backend. The design follows the current API contract and
optimizes for:

- the smallest practical number of tables;
- point reads and point writes by `PartitionKey` + `RowKey`;
- minimal duplicated data;
- simple cleanup;
- reliable one-time barcode consumption without keeping barcode history.

The scanner survey table is intentionally outside this design. It already
exists as a temporary admin tool for scanner compatibility testing.

## Tables

```text
CustomerProfiles
DiscountRuntime
AuditEvents
```

No separate profile index, barcode index, SMS challenge table, barcode history
table, or POS client table is used in the MVP.

POS HMAC secrets are stored in server-side configuration or Key Vault, not in
Azure Table Storage.

## Common Key Rules

- Values already present in `PartitionKey` or `RowKey` are not duplicated as
  ordinary entity properties unless they are needed in a returned API response
  or export.
- Random ids are generated only by the backend.
- When a random key is inserted, the backend uses Azure Table `Insert`. If the
  table returns a conflict, the backend generates a new value and retries.
- Date/time values are stored as UTC timestamps.
- Raw phone numbers are stored only where they are needed for the business
  flow. Audit stores `PhoneHash` instead of raw phone.

## CustomerProfiles

Stores one saved customer profile per normalized phone number.

```text
Table: CustomerProfiles
PartitionKey: phone
RowKey: <normalized phone without +>
```

Example key:

```text
PartitionKey: phone
RowKey: 380501234567
```

The `RowKey` is generated by the backend from the normalized Ukrainian phone
number. This key enforces the rule: one phone number equals one person and one
profile.

Creating a duplicate profile is prevented by Azure Table `Insert` conflict on
the same `PartitionKey` + `RowKey`.

Entity:

```json
{
  "PartitionKey": "phone",
  "RowKey": "380501234567",
  "Phone": "+380501234567",
  "AnswersJson": "[{\"code\":\"fullName\",\"name\":\"ФИО\",\"value\":\"Ivan Petrenko\"},{\"code\":\"birthDate\",\"name\":\"День рождения\",\"value\":\"1990-04-15\"},{\"code\":\"favoriteDish\",\"name\":\"Любимое блюдо\",\"value\":\"Pizza Margherita\"}]",
  "CreatedAtUtc": "2026-06-16T13:55:00Z",
  "UpdatedAtUtc": "2026-06-16T13:55:00Z"
}
```

Fields:

| Field | Use |
| --- | --- |
| `PartitionKey` | Constant `phone`; groups customer profile rows separately from other tables and keeps lookup simple. |
| `RowKey` | Normalized phone without `+`; primary lookup key for admin, public redemption, and POS profile lookup. |
| `Phone` | Normalized display/API phone value with `+`; returned to API clients and POS. |
| `AnswersJson` | Serialized `answers[]` array with `code`, `name`, `value`; stored as one value because profiles are small and read/written as a whole. |
| `CreatedAtUtc` | Profile creation time; returned to admin API and useful for support. |
| `UpdatedAtUtc` | Last profile update time; returned to admin API and useful for support. |

Why this is optimal for the MVP:

- every required profile lookup is by phone;
- no separate `ProfileId` is needed;
- no secondary profile index is needed;
- no duplicated profile records need to be kept in sync;
- create, read, and update are single-row operations.

## DiscountRuntime

Stores the current temporary redemption state for one phone number. SMS
verification and the active barcode are stored in the same entity. There is only
one runtime row per phone, so a new redemption flow for the same phone
overwrites the previous SMS challenge and previous barcode automatically.

```text
Table: DiscountRuntime
PartitionKey: phone:<phoneRuntimeKey>
RowKey: current
```

Example key:

```text
PartitionKey: phone:p_7K3F9Q2M
RowKey: current
```

`phoneRuntimeKey` is generated by the backend from the normalized phone using a
server-side secret, for example HMAC-SHA256 with truncation and URL-safe
encoding. It must be deterministic for the same normalized phone, but it must
not expose the raw phone number.

This key structure enforces the MVP rule that only one current runtime flow and
one active barcode can exist for a phone.

Entity:

```json
{
  "PartitionKey": "phone:p_7K3F9Q2M",
  "RowKey": "current",
  "Phone": "+380501234567",
  "CorrelationId": "c_01K8WJ4D6Q7X9M2P5A3C",
  "SmsCodeHash": "hmac-sha256:...",
  "SmsAttempts": 0,
  "SmsMaxAttempts": 3,
  "SmsSentAtUtc": "2026-06-16T14:00:00Z",
  "SmsExpiresAtUtc": "2026-06-16T14:03:00Z",
  "PhoneVerifiedAtUtc": null,
  "BarcodeHash": null,
  "BarcodeExpiresAtUtc": null,
  "BarcodeConsumedAtUtc": null,
  "ConsumedByScanId": null,
  "CreatedAtUtc": "2026-06-16T14:00:00Z",
  "UpdatedAtUtc": "2026-06-16T14:00:00Z"
}
```

Fields:

| Field | Use |
| --- | --- |
| `PartitionKey` | `phone:<phoneRuntimeKey>`; deterministic opaque phone key used for point reads from frontend SMS verification and POS barcode validation. |
| `RowKey` | Constant `current`; keeps exactly one current runtime row per phone. |
| `Phone` | Normalized phone with `+`; required because successful POS barcode validation returns phone as lookup key. |
| `CorrelationId` | Random trace id generated by backend when redemption starts; overwritten when a new redemption flow starts for the same phone. Used in API errors, audit partitioning, and support. |
| `SmsCodeHash` | HMAC/hash of the SMS code; the raw SMS code is not stored. |
| `SmsAttempts` | Count of invalid SMS verification attempts for the current SMS code. Reset when a new redemption flow overwrites the row. |
| `SmsMaxAttempts` | Maximum attempts for the current SMS code; MVP value is `3`. |
| `SmsSentAtUtc` | Last SMS send time; used for diagnostics and retry throttling if resend is added/used in the same flow. |
| `SmsExpiresAtUtc` | SMS code expiration; SMS verification rejects requests after this time. |
| `PhoneVerifiedAtUtc` | Set when SMS verification succeeds; replaces a separate technical status field. Reset to `null` when a new redemption flow starts. |
| `BarcodeHash` | HMAC/hash of the full active barcode. Set after successful SMS verification. Cleared after successful POS validation or when a new flow overwrites the row. |
| `BarcodeExpiresAtUtc` | Barcode expiration; POS validation rejects requests after this time. |
| `BarcodeConsumedAtUtc` | Set when POS validation succeeds; used to reject second use as `already_used`. Reset to `null` when a new barcode is issued. |
| `ConsumedByScanId` | POS scan/sale id that successfully consumed the barcode. Used to make retry of the same POS validation idempotent. Reset to `null` when a new barcode is issued. |
| `CreatedAtUtc` | Creation time of the current redemption flow stored in the runtime row. |
| `UpdatedAtUtc` | Last overwrite/update time. Needed because the same runtime row is reused for later flows for the same phone. |

Fields intentionally not stored:

| Field | Reason |
| --- | --- |
| `RedemptionId` | No longer needed as a storage key; `phoneRuntimeKey` addresses the current runtime row. |
| `BarcodeValue` | The active barcode is short-lived but contains the phone runtime key; storing only `BarcodeHash` avoids keeping active barcode values in storage. |
| `PhoneHash` | Runtime needs raw `Phone`; hash is computed when writing audit events. |
| `SmsCreatedAtUtc` | Covered by `CreatedAtUtc`, `UpdatedAtUtc`, and `SmsSentAtUtc`. |
| `BarcodeCreatedAtUtc` | Barcode is issued immediately after phone verification; exact issue event is in `AuditEvents`. |
| `FailedAtUtc` | SMS failure can be inferred from attempts and audit events. |
| `CompletedAtUtc` | Barcode completion is represented by `BarcodeConsumedAtUtc`. |

### Runtime Flow

`POST /api/public/redemptions`:

1. Generate new `CorrelationId` as soon as the request reaches business
   handling.
2. Write `redemption_started` to `AuditEvents` with
   `PartitionKey = CorrelationId`.
3. Normalize phone. If normalization fails, write `invalid_phone` to
   `AuditEvents` and return an error response with `correlationId`.
4. Read `CustomerProfiles` by phone key.
5. If the profile is not found, write `profile_not_found` to `AuditEvents` and
   return an error response with `correlationId`; do not create or update
   `DiscountRuntime`.
6. If the profile is found, generate deterministic `phoneRuntimeKey` from the
   normalized phone.
7. Generate SMS code and store only `SmsCodeHash`.
8. Upsert the `DiscountRuntime` entity at
   `PartitionKey = phone:<phoneRuntimeKey>`, `RowKey = current`.

The `AuditEvents` row exists even when the process stops before SMS or before
barcode generation. This is what allows admin/support QR lookup by
`correlationId` for early failures.

The `DiscountRuntime` upsert happens only after the customer profile is found.
It overwrites any previous current flow for the same phone. This is the
mechanism that invalidates any previous SMS challenge or barcode for that phone
without an extra index table or transaction.

Initial/overwritten fields:

```text
Phone = normalized phone
CorrelationId = new trace id
SmsCodeHash = hash of new SMS code
SmsAttempts = 0
SmsMaxAttempts = 3
SmsSentAtUtc = now
SmsExpiresAtUtc = now + sms TTL
PhoneVerifiedAtUtc = null
BarcodeHash = null
BarcodeExpiresAtUtc = null
BarcodeConsumedAtUtc = null
ConsumedByScanId = null
CreatedAtUtc = now
UpdatedAtUtc = now
```

The public API returns `redemptionKey = phoneRuntimeKey`. The key is opaque and
does not expose the raw phone.

`POST /api/public/redemptions/{redemptionKey}/sms-verifications`:

1. Read `DiscountRuntime` by `PartitionKey = phone:<redemptionKey>`,
   `RowKey = current`.
2. Reject if the row is missing.
3. Reject if `now > SmsExpiresAtUtc`.
4. Reject if `SmsAttempts >= SmsMaxAttempts`.
5. Reject if `PhoneVerifiedAtUtc` is already set.
6. If code is wrong, increment `SmsAttempts` and set `UpdatedAtUtc = now`.
7. If code is correct, set `PhoneVerifiedAtUtc`, generate barcode, store
   `BarcodeHash`, set `BarcodeExpiresAtUtc`, reset `BarcodeConsumedAtUtc` to
   `null`, reset `ConsumedByScanId` to `null`, and set `UpdatedAtUtc = now`.

Barcode format:

```text
SDV-<phoneRuntimeKey>-<correlationId>
```

Example:

```text
SDV-p_7K3F9Q2M-c_01K8WJ4D6Q7X9M2P5A3C
```

The barcode includes `phoneRuntimeKey` so POS validation can perform one point
read without a separate barcode index table. It also includes `correlationId`
so restaurant staff can report the scanned barcode to support and support can
query `AuditEvents` directly by `PartitionKey = correlationId`.

For the MVP, `correlationId` also acts as the random barcode component. This is
an accepted tradeoff because the barcode is short-lived, one-time, and POS
validation stores `ConsumedByScanId` for idempotent retry handling. The full
barcode value is not stored; only `BarcodeHash` is stored and compared during
validation.

`POST /api/pos/barcodes/validate`:

1. Validate HMAC headers.
2. Require `scanId`. POS must send the same `scanId` when retrying the same
   scan/sale validation.
3. Parse `phoneRuntimeKey` and `correlationId` from `barcodeValue`.
4. Read `DiscountRuntime` by `PartitionKey = phone:<phoneRuntimeKey>`,
   `RowKey = current`.
5. Return `invalid_format` if the barcode cannot be parsed.
6. Return `unknown` if the runtime row is missing.
7. Return `unknown` or `invalid_format` if parsed `correlationId` does not
   match runtime `CorrelationId`.
8. If `BarcodeConsumedAtUtc` is set and `ConsumedByScanId` equals
   `request.scanId`, return the successful validation response again with
   `idempotentReplay: true`.
9. If `BarcodeConsumedAtUtc` is set and `ConsumedByScanId` is different from
   `request.scanId`, return `already_used`.
10. Return `expired` if `now > BarcodeExpiresAtUtc`.
11. Return `unknown` if `BarcodeHash` is missing.
12. Hash the full scanned barcode and compare it with stored `BarcodeHash`.
13. Return `unknown` or `invalid_format` if the hash does not match.
14. On first success, conditionally update the row by ETag:

```text
BarcodeHash = null
BarcodeConsumedAtUtc = now
ConsumedByScanId = request.scanId
UpdatedAtUtc = now
```

The ETag conditional update is the reliability mechanism that prevents two
parallel POS validations from consuming the same barcode successfully.

If the ETag update succeeds, return `valid: true` with
`idempotentReplay: false`. If the POS does not receive that response and retries
with the same `scanId`, the already-consumed row returns the same successful
business result with `idempotentReplay: true`.

Cleanup:

- Delete runtime rows after all temporary data is safely expired.
- A simple retention rule is enough for MVP, for example delete rows where
  `UpdatedAtUtc` is older than the configured runtime retention window.

## AuditEvents

Stores append-only audit and diagnostic events. Audit is separate from runtime
data because it has a different retention period and must remain available
after temporary runtime records are cleaned up.

```text
Table: AuditEvents
PartitionKey: <correlation id>
RowKey: <timestamp>_<random event suffix>
```

Example key:

```text
PartitionKey: c_01K8WJ4D6Q7X9M2P5A3C
RowKey: 20260616T140412123Z_ae_F7K2Q9
```

The backend generates `RowKey` from UTC time plus a random suffix. If insert
conflicts, the backend generates a new suffix and retries.

Entity:

```json
{
  "PartitionKey": "c_01K8WJ4D6Q7X9M2P5A3C",
  "RowKey": "20260616T140412123Z_ae_F7K2Q9",
  "EventType": "barcode_validation_succeeded",
  "PhoneHash": "sha256:...",
  "ActorType": "pos",
  "ActorId": "main-pos-system",
  "OccurredAtUtc": "2026-06-16T14:04:12Z",
  "MetadataJson": "{\"terminalId\":\"POS-01\",\"branchId\":\"kyiv-obolon\"}"
}
```

Fields:

| Field | Use |
| --- | --- |
| `PartitionKey` | `CorrelationId`; querying one partition returns the event chain for one redemption flow. |
| `RowKey` | Sortable event key built from timestamp and random suffix. |
| `EventType` | Business or technical event name. |
| `PhoneHash` | Supports phone-related diagnostics without storing raw phone in audit. Present when the phone was successfully normalized; may be `null` for early errors such as `invalid_phone`. |
| `ActorType` | Actor category, such as `customer`, `admin`, `pos`, or `system`. |
| `ActorId` | Actor identifier where known, such as POS client id or admin identity. |
| `OccurredAtUtc` | Event time. |
| `MetadataJson` | Small event-specific payload, such as terminal id, branch id, POS `scanId`, error code, or barcode validation reason. |

Fields intentionally not stored:

| Field | Reason |
| --- | --- |
| `CorrelationId` | Equal to `PartitionKey`; duplicate storage is unnecessary for MVP. |
| raw `Phone` | Audit should avoid raw phone; use `PhoneHash`. |

No `AuditEventsByPhoneHash` table is included in the MVP. If support later
requires frequent lookup by phone hash, an index table can be added without
changing the main write model.

## Id Generation Summary

| Value | Generated by | When | Uniqueness guarantee |
| --- | --- | --- | --- |
| Customer profile `RowKey` | Backend | Admin create/update phone normalization | Deterministic normalized phone; Azure Table insert conflict prevents duplicates. |
| `phoneRuntimeKey` / `DiscountRuntime.PartitionKey` suffix | Backend | Start redemption and POS barcode parsing | Deterministic HMAC/opaque key from normalized phone; same phone always maps to the same runtime row without exposing raw phone. |
| `CorrelationId` | Backend | Start redemption | Cryptographically random trace id; practical uniqueness. |
| `BarcodeValue` | Backend | Successful SMS verification | Contains `phoneRuntimeKey` plus `correlationId`; full value is returned to frontend, hashed into `BarcodeHash`, and not stored raw. |
| `AuditEvents.RowKey` | Backend | Each audit event | UTC timestamp plus random suffix; Azure Table insert conflict retry. |

## Cost And Reliability Rationale

- `CustomerProfiles` reads are point reads by normalized phone.
- `DiscountRuntime` reads are point reads by `phoneRuntimeKey`, including POS
  barcode validation because the barcode contains `phoneRuntimeKey`.
- A new redemption flow for the same phone overwrites one existing row, so the
  storage shape itself enforces one active runtime flow and one active barcode
  per phone.
- `AuditEvents` queries are partition queries by `CorrelationId`.
- There are no secondary index tables to maintain.
- There is no barcode history table to clean or reconcile.
- Runtime state transitions are represented by concrete timestamps rather than
  a separate status field.
- One-time barcode reliability depends on ETag conditional update, not on
  timing assumptions.
